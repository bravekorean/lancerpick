# LancerPick 자기소개서·포트폴리오 관리 기준

4인 팀의 서비스 소개는 루트 README에 두고, 지원 문서에서는 내가 맡은 적립금 충전·지갑 결제·환불·정산 중 한 장면을 고른다. 면접관이 “누구에게 어떤 문제가 생겼고, 지원자가 무엇을 판단했는가?”에 답할 수 있는 사례를 우선한다.

## 자기소개서에 옮길 때

한 사례를 2~3문장으로 쓴다. 첫 문장은 사용자가 겪을 문제, 다음 문장은 내가 구현한 처리, 마지막 문장은 테스트에서 확인한 결과를 담는다. 아래는 충전 복구 사례의 초안이다.

> LancerPick에서 적립금 충전을 맡으며, 토스가 결제를 승인한 직후 응답이 끊기면 사용자가 결제한 금액이 지갑에 들어오지 않을 수 있다는 점을 확인했습니다. 기존 결제 식별자로 승인 결과를 다시 조회해 확인된 금액을 지급하고, 복구 작업도 중간에 실패하면 이어서 실행할 수 있도록 구현했습니다. 토스 테스트 대역으로 첫 건 지급 후 작업을 실패시킨 뒤 재시작했을 때, 첫 건을 다시 조회하거나 지급하지 않고 두 번째 충전을 완료했습니다.

## 포트폴리오에 펼칠 때

| 면접관의 질문 | 충전 복구 사례에서 설명할 내용 |
| --- | --- |
| 어떤 문제가 생기는가? | 사용자는 결제했는데 적립금이 들어오지 않을 수 있다. 이 사례의 출발점은 결제사 승인 직후 응답이 끊기는 상황이다. |
| 왜 단순 재시도로 해결하기 어려운가? | 응답이 없다는 사실만으로 승인 여부를 판단할 수 없다. 저장한 결제 식별자로 토스의 기록을 확인해야 지급 여부를 정할 수 있다. |
| 대안은 무엇이고 현재 구현은 무엇을 얻는가? | 스케줄러로 미확정 건을 주기적으로 다시 조회할 수 있다. 현재 구현에서도 스케줄러가 실행 주기를 맡는다. Spring Batch를 함께 쓰면 실패한 실행의 이력과 마지막 처리 위치를 저장하고 같은 작업을 이어갈 수 있다. |
| 그 선택으로 무엇을 더 관리해야 하는가? | Flyway로 배치 메타데이터 테이블을 관리한다. 지급 커밋과 체크포인트 저장 사이에 작업이 멈춰도 다시 지급하지 않도록 충전 상태와 원장의 유일 제약을 함께 사용한다. |
| 어디까지 확인했는가? | 테스트 대역에서 첫 건 지급 후 다음 후보 조회를 실패시켰다. 같은 JobInstance를 재시작해 첫 건의 추가 조회·지급 없이 둘째 건이 완료되는지 확인했다. [통합 테스트](../LancerPick/src/test/java/com/example/lancerpick/wallet/TopupRecoveryIntegrationTests.java#L561) |

## 사례를 갱신할 때

- 기능이나 테스트가 달라지면 [변경 이력](change-history.md)에 환경·재현 조건·기대값·실제 결과를 먼저 기록한다. 이어서 [사례별 근거 표](README.md#portfolio-evidence)의 해당 행과 그 근거를 인용한 소개 문장을 갱신한다.
- 당시 검토한 대안과 면접 준비 중 사후에 비교한 대안을 구분한다. 개인 기여는 담당 코드와 확인한 작업 범위 안에서 쓴다.
- 같은 지갑의 동시 결제는 성공·실패 건수와 최종 잔액으로, 취소와 구매 확정의 경합은 보관금과 판매자 지급 결과로 설명한다. 긴 잠금 대기와 실패 후 재시도는 2026-11-28에 통합 테스트로 확인했다([검증](change-history.md#wallet-lock-crash-recovery-check)). 대기 한도 초과가 HTTP 500으로 응답한다는 점은 개선 전 한계로 함께 적는다.
- 개선 후 더미 데이터 100만 건 이상을 넣는 실험은 계획 단계다. 실행하면 데이터 분포·요청 패턴·동시성·측정 구간을 결과와 함께 기록한다. 정확성과 복구를 보여주는 사례는 해당 테스트 결과만으로 설명할 수 있다.
