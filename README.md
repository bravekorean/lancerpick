# 랜서픽 | LancerPick

프리랜서의 고정 가격 서비스를 주문하고, 결제부터 납품·구매 확정·정산까지 진행하는 4인 팀 프로젝트입니다.

**황준범 · 결제 · 적립금 지갑 · 환불 · 정산**

결제 영역의 백엔드와 화면 연동을 맡았고, DB 스키마·Flyway 마이그레이션과 React 공통 API·캐시 구성에 기여했습니다.

`Java` · `Spring Boot` · `Spring Data JPA / QueryDSL` · `MySQL / Flyway` · `Spring Batch` · `React / TypeScript`

## 결제·환불·정산의 금액 일관성

- 같은 주문의 결제 요청이 겹치면 주문 잠금 아래에서 기존 결제 기록을 확인해 중복 차감을 막았습니다. 서로 다른 주문이 같은 지갑을 쓰는 경우에는 지갑 행 잠금으로 잔액 확인과 차감을 순서대로 처리했습니다.
- 주문 상태 변경, 지갑 차감, 결제·보관금·원장·아웃박스 기록을 하나의 트랜잭션으로 묶었습니다. 구매 확정 시 수수료를 제외한 금액을 판매자에게 지급하고, 취소가 승인되면 구매자에게 반환하도록 연동했습니다.
- 같은 주문에 **24회 요청해도 차감은 1회**만 발생함을 확인했습니다. 공유 지갑의 잔액 부족 처리와 중간 예외 시 롤백도 MySQL에서 검증했습니다. [결제·보관·지급·환불 설계](docs/features.md#finance-funds) · [동시 결제 검증](docs/change-history.md#payment-concurrency-benchmark)

## 토스 승인 응답이 끊긴 충전 복구

토스가 승인한 직후 응답이 끊기면 내부에서는 결과를 확정할 수 없습니다. 미확정 상태로 남긴 건은 Spring Batch가 기존 결제 식별자로 승인 결과를 조회하고, 확인된 금액만 지갑과 원장에 반영하도록 구현했습니다. 외부 응답을 기다리는 구간을 지갑 갱신 트랜잭션과 분리했습니다.

로컬 MySQL과 토스 테스트 대역에서 **960건을 복구 검증**했습니다. 각 실행 직후 배치를 다시 실행한 **18회 모두 추가 승인 조회와 중복 지급이 0건**이었습니다. [복구 방식](docs/features.md#finance-batch) · [검증 결과](docs/change-history.md#topup-recovery-benchmark)

## 결제 성능 개선

같은 지갑으로 여러 주문을 동시에 결제할 때, 지갑을 잠근 트랜잭션 안에서 중복 잠금 조회와 주문 상세 조회가 실행되고 있었습니다. 이미 잠근 주문을 재사용하고, 주문당 최대 한 건인 결제·수정 요청·후기를 기본 상세 조회에 합쳤습니다. 납품·취소 요청·이력처럼 여러 행이 나오는 데이터는 별도로 읽어 조인 결과가 불어나지 않도록 했습니다.

| 지표 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 신규 결제 1건당 SQL | 32회 | **27회 (15.6% 감소)** |
| 결제 응답용 주문 상세 SQL | 7회 | **4회** |
| 주문 상세 조회 시간 | 6.36ms | **4.12ms (35.1% 감소)** |
| 결제 서비스 응답시간 p95 | 167.68ms | **157.22ms (6.2% 감소)** |

시간은 격리된 로컬 MySQL에서 같은 지갑에 8개 작업자가 결제를 요청하는 조건을 역순으로 재측정한 값입니다. 상세 조회 개선 전후 **1,248건**의 테스트 요청에서 금액 검증 실패와 예상 밖 오류가 0건이었고, **회귀 테스트 162개**가 통과했습니다. [측정 조건과 원본 데이터](docs/change-history.md#finance-verification-summary)

## 거래 화면 개선

- **판매 수익**에서 상품명·주문번호로 검색하면 목록과 합계에 같은 조건이 적용되도록 연결했습니다. 지갑 원장을 확인해 실제 적립금 지급과 수익 기록만 남은 기존 거래를 화면에서 구분했습니다.
- **거래 상세**를 거래 진행·계약 및 조건·거래 기록 세 탭으로 나눴습니다. 탭을 옮겨도 작성 중인 입력을 유지하고, 320px 화면에서 가로 넘침 없이 탐색할 수 있는지 확인했습니다. [판매 수익 기능](docs/features.md#finance-settlement) · [거래 화면 검증](docs/change-history.md#v3-representative-trade-check)
